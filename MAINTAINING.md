# Maintaining this fork

This is a full fork of
[cloudnative-pg/postgres-containers](https://github.com/cloudnative-pg/postgres-containers).
It tracks upstream and adds `extra` image variants carrying Citus and PostGIS,
publishing everything to `ghcr.io/maarlab-rethinking`.

## One-time setup per clone

```bash
git remote add upstream https://github.com/cloudnative-pg/postgres-containers.git
git config merge.ours.driver true
```

The second line enables the `merge=ours` driver that
[`.gitattributes`](.gitattributes) relies on to keep our generated image
catalogs on every merge. Without it every one of those files has to be
resolved by hand each time; git falls back to an ordinary conflict, never to a
wrong resolution.

## Bringing in upstream changes

```bash
git fetch upstream
git merge upstream/main
```

Then, before committing the merge:

1. **Line up the Debian base images.** An upstream digest bump lands in
   `docker-bake.hcl` only, so the copy the extra targets keep goes stale:

   ```bash
   hack/sync-base-images.sh
   ```

2. **Resolve every target.** This is what catches a new PostgreSQL major that
   the extension maps do not cover yet -- the failure mode that arrived with
   19~beta3:

   ```bash
   docker buildx bake -f docker-bake.hcl --print > /dev/null
   docker buildx bake -f docker-bake.hcl -f docker-bake.extra.hcl --print all > /dev/null
   ```

   A major with no Citus/PostGIS mapping is skipped by the `extra` targets on
   purpose, and still builds as `minimal`, `standard` and `system`. To offer
   the extra variants for it, add the major to `extensionsVersionMap` in
   `docker-bake.hcl`.

### When upstream retires a Debian release

`merge=ours` does not cover it. Deleting a file we have modified is a
modify/delete conflict, which is resolved at the tree level and never reaches
a merge driver, so the catalogs for the retired release arrive conflicted and
have to be `git rm`-ed. The release then has to come out of
`docker-bake.extra.hcl` by hand in three places -- the `<distro>Image`
variable, the `extra-targets` base list, and any entry in
`extensionDistroConstraints`. `hack/sync-base-images.sh` refuses to pass until
that is done, naming the release it still finds. Bullseye went this way in
September 2026, when its Debian LTS ended and every build on it started
404-ing.

Anything the merge breaks belongs in the merge commit itself, not in a
follow-up fix.

[`.github/workflows/validate.yml`](.github/workflows/validate.yml) runs both
of these checks on push and on pull requests, so a mistake here surfaces in
CI rather than in the next scheduled build.

## What diverges from upstream, and why

| Path | Divergence |
|---|---|
| `docker-bake.hcl` | Kept as close to upstream as possible. Only the fork's `url`, `PRELOAD_LIBRARIES`, `extensionsVersionMap` and the `getExtensionsString` that pins extension versions. `target "default"` is byte-identical, so Renovate's digest bumps merge cleanly. |
| `docker-bake.extra.hcl` | Fork only: the `extra` targets, the extension constraints and their own copy of the base images. |
| `Dockerfile` | Adds the `extra` stage and wires `shared_preload_libraries`. |
| `Debian/ClusterImageCatalog-*` | Generated by our CI against our registry. Never take upstream's. |
| `.github/workflows/catalogs.yml` | Publishes to `maarlab-rethinking/artifacts`, and toggles branch protection with `gh api` instead of the action described below. |
| `.github/workflows/bake_update.yml` | Same branch-protection replacement. |
| `CODEOWNERS` | `@maarlab-rethinking/engineering`. |

## The branch-protection action

Upstream toggles the `enforce_admins` branch protection with
`benjefferies/branch-protection-bot` around the steps that commit to `main`.
That action is a Docker action built `FROM python:3.12.0-slim-bullseye`, and
GitHub builds Docker actions before the first step runs, so once bullseye went
EOL it took down whole jobs -- `Update PostgreSQL versions` and
`Update Catalogs` -- before they could check anything out. Its last release is
from November 2023, so no fix is coming.

Both workflows now call `gh api` on
`repos/{owner}/{repo}/branches/main/protection/enforce_admins` directly: GET
to record the current value, DELETE to turn it off, POST to put it back only
if it had been on. A `404 Branch not protected` is treated as "nothing to do",
which is in fact this fork's situation -- `main` here is unprotected, so the
whole dance is a no-op and only matters upstream.

Revert this if upstream ever replaces the action.

## Sending something back upstream

Work that is not fork-specific is worth a pull request against
`cloudnative-pg/postgres-containers`. Branch from `upstream/main` rather than
from `main`, so the change does not carry any of the divergence above.
